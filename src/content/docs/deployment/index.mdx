Recipery ships as a single container image
(`ghcr.io/recipery-dev/recipery:latest`) with no database — deploying it is
really two independent choices: which platform runs the container, and
where recipes are stored. This section covers the platform; see
[Storage](/storage) for the storage backends.

<CardGrid>
  <Card title="Docker" icon="ph:cube">
    A `docker run` or Compose file — the fastest way to try Recipery or
    run it on a single machine. See [Docker](/deployment/docker).
  </Card>
  <Card title="Cloudflare" icon="ph:cloud">
    Deploy the app itself as a Cloudflare Worker, backed by a native R2
    binding. See [Cloudflare](/deployment/cloudflare).
  </Card>
  <Card title="Kubernetes" icon="ph:stack">
    Example manifests for running the container in a cluster. See
    [Kubernetes](/deployment/kubernetes).
  </Card>
</CardGrid>

## Which one should I use?

| Platform | Good for | Storage |
| --- | --- | --- |
| [Docker](/deployment/docker) | Trying Recipery, single-machine self-hosting | [Local](/storage/local), [S3](/storage/s3), or [R2](/storage/cloudflare-r2) |
| [Cloudflare](/deployment/cloudflare) | Running with no server to maintain | R2 only, via a native binding |
| [Kubernetes](/deployment/kubernetes) | Running alongside other self-hosted services in a cluster | [S3](/storage/s3) or [R2](/storage/cloudflare-r2) recommended — see the caveat on local disk |

<Aside type="note" title="No official Helm chart">
  There's no packaged Helm chart yet — the [Kubernetes](/deployment/kubernetes)
  page gives you plain manifests to adapt.
</Aside>
